# Findings

Everything the function campaigns turned up, in four groups: what the mesh does
wrong, what the instrument does wrong, what the harness does wrong, and what the
documents claimed that the code does not do. Each entry says how to see it.

Unless an entry says otherwise, the environment is the deployment
`bench/bench.sh deploy` leaves behind: one node, `K=8`, 32 execution units,
namespace `test-bench`.

---

## 1. The mesh

The two entries this section used to hold — a retry policy that retried nothing,
and a route-targeted `AuthorizationPolicy` that admitted nobody — were not mesh
defects. Both were fixtures asking the stock policy controller for something it
does not offer on the kind of route they were written on, and in neither case
did what reached the proxy resemble the policy anyone had read. They are
[3.6](#36-a-grpc-retry-condition-was-written-on-a-route-that-cannot-carry-one)
and [3.7](#37-an-inbound-route-was-written-in-a-kind-its-server-does-not-carry),
with the controller's own answer as the evidence.

What this section does hold is three defects the campaigns did not set out to
look for, all of them now closed.

### 1.1 A worker could spin until nothing on it answered

Two of the eight ARM workers were found at 99.9% CPU with the cluster idle and
no traffic anywhere, and their Linkerd admin endpoints answering nothing —
`discover_admin_ports` listed seven ports instead of eight. Neither cleared on
its own; both were still spinning when they were read again six hours later,
which is what made the rest of this entry possible.

```sh
bash bench/bench.sh dpucpu                    # dmesh-w4, dmesh-w5 at 99.9%
ssh "$DPU_HOST" 'curl -sf --max-time 4 127.0.0.1:4195/metrics'   # nothing
```

**The admin endpoint was the window, not the extent of it.** The port is not
refused, it is unanswered: the socket is bound, the kernel has completed
handshakes nobody accepts, and `/live` — which reads no metric and takes no
lock — times out with everything else.

```text
LISTEN 0 128 127.0.0.1:4194     healthy
LISTEN 7 128 127.0.0.1:4195     seven connections completed, none accepted
LISTEN 9 128 127.0.0.1:4196     nine
```

The admin server is not on the worker thread. It has a thread of its own and a
runtime of its own, and that thread is asleep. What wakes it is the *worker*
runtime's driver, because that is where its listener is registered — together
with the worker's inbound and outbound listeners. A worker whose driver stops
running stops serving everything it was given; the admin port is only the part
of that a campaign can see.

**The driver stops running because the datapath pass never waits.** Three
syscalls per pass and nothing else, twelve thousand passes a second, and not one
poll of the runtime's own epoll:

```text
healthy worker, 3s            wedged worker, 3s
  2771 epoll_pwait(driver)       0 epoll_pwait(driver)
  1372 write(unpark)             0 write(unpark)
  1375 datapath pass         36408 datapath pass
```

That pass waits on a `select!` of three notification fds, a maintenance deadline
and `poll_internal`. The fds need the driver, which is not running; the deadline
is in the future; so `poll_internal` is what completes it, synchronously, every
time. And it answered on `tx_finished()`, which is `tx_closed && tx_queued() ==
0` — the *state* of a closed write half, not an event. A drain publishes that
side's FIN once and records it; a session closes only when every side has
finished. So one session another endpoint keeps open answers "there is work"
forever while the drain has nothing left to do about it, and the pass never
reaches its wait.

That also explains the fan-out arm's four-channel stage returning no reading
while its one-channel stage was normal: a session that lands on a worker which
accepts nothing is served by nothing. Which worker a session lands on is not
recorded, so that pairing is still a reading rather than a demonstration.

**The fix** is in two places, because the condition and the shape of it are
different problems:

- `Worker::poll_internal` (`linkerd/rust/src/lib.rs`) no longer counts a FIN the
  datapath has already accepted. That removes the permanent answer, and the side
  goes on to register the driver waker the old test skipped past.
- The runtime loop (`linkerd/port/…/linkerd/doca/src/runtime.rs`) drops the
  internal poll from the wait after one wake that publishes nothing, until a
  notification, a drain that progresses or the maintenance deadline says
  something moved. Two conditions of the same shape stay reachable — a refused
  `tx_finish`, and queued bytes no arena chunk can carry — and this bounds both
  to the millisecond maintenance period instead of a spin. Nothing is dropped:
  every pass drains before it waits.

`unpublishable_internal_work_does_not_spin` is the regression test: a backend
that reports work on every ask and publishes none of it must still reach its
wait. Without the guard it takes the internal branch on every pass and never
sleeps once.

Readings are in
[`worker-spin-diagnosis.txt`](f-fix3-20260822-020539/worker-spin-diagnosis.txt),
the first stacks in
[`worker-spin.txt`](f-fix3-20260822-020539/worker-spin.txt).

### 1.2 The protocol-aware path stops accepting connections

A stage gets no reading, and what it gets instead is the client saying it could
not start:

```text
S14 [FAIL] the failing endpoint withdrawn: ERR connect failed on channel 0
```

`ERR connect failed on channel 0` is `WaitForConnected` giving up after twenty
seconds. The DPU logs one line for each attempt and nothing else:

```text
px_poison: poisoning conn (11:200): Linkerd session ended before both output FINs
```

That message is the datapath reporting what the adapter told it:
`dmesh_l7_session_failed` is called from `Worker::drain` when `pump_side`
returns an error, and the error it returns for a connection that never carried
a byte is `tx_aborted` — the Linkerd stack dropped the endpoint without shutting
it down. So the connection reaches the proxy and the proxy discards it.

**It is not one stage.** It first appeared at `S14` five times running, which is
what named this entry. It is not bound there:

| Run | Failed |
|---|---|
| four `surfaces` runs, two builds | `S14` only — 19/20 |
| a fifth, with the DPU log captured | `S11`, `S12`, `S13`; `S14` served — 16/20 |
| a sixth, on the same DPU | seventeen of twenty; `S3a`, `S5` and `S15` served |

The two paths beside it are untouched throughout — the native arm and the
opaque-L7 arm both serve while the protocol-aware arm refuses everything.

**It is not the balancer.** The outbound HTTP balancer for that Service holds no
endpoints and has never taken an `Add`, which looked like the answer until it
was sampled every five seconds through a whole run: it reads zero during the
stages that serve as well as the ones that fail. A backend on this node is
reached through the DPUmesh connector, not by dialling an endpoint, so an empty
HTTP balancer is what this architecture looks like.

**A campaign leaves sessions behind, and one stage is where they come from.**
A connection the inbound policy refuses is retried, and about seven in a hundred
of the sessions those retries open never close:

```text
H3 route withdrawn        active=0    opened=5
H4 inbound Server, deny   active=79   opened=1109      one ten-second stage
H7 a plain point again    active=79   rcnt=7870 fail=0
```

`surfaces` runs that stage twice, at `S10` and `S12`. The held sessions drain at
roughly one every thirty-five seconds, which is the same curve as the two
behaviours that looked contradictory: a campaign that ends holding few recovers
within minutes, one that ends holding many stays refusing through repeated
attempts and a Deployment roll.

**That leak is not the connect failure, though.** `H7` above is a plain point
taken with all seventy-nine still held, and it serves. The count travels with
the failure without being enough to cause it — which is a real defect of its
own, and the one thing in this entry that reproduces in a single command
([`reduction-what-leaks-sessions.sh`](f-spin-20260822/reduction-what-leaks-sessions.sh)).

**The withdrawal is not the trigger, and neither is any single stage.** Six
reductions were run against a freshly deployed DPU, each ending in the `S13` →
`S14` sequence, and every one of them served:

| What was reproduced before the withdrawal | `S14` |
|---|---|
| nothing — bring the failing endpoint up and withdraw it | serves |
| replace the Service's own Pod, and ask again at 20 s and at 65 s | serves |
| the breaker annotations and traffic through the failing endpoint, so the breaker verifiably ejects it — the broken Pod serves exactly 3 requests and then none | serves |
| the three stages whose requests match no rule, ~24,000 refusals each, as `S5`, `S7` and `S9` do | serves |
| two rolls of the Service's own Deployment, which is what `grpc_fail_every` does at `S3` | serves |
| an inbound `Server` and an `AuthorizationPolicy` applied and withdrawn, as `S10`–`S12` do | serves |

Every one of them also left the DPU holding no sessions, which is the thing they
have in common and the thing they fail to reproduce.

**Open.** It is not [1.1](#11-a-worker-could-spin-until-nothing-on-it-answered)'s
fix: that fix was reverted, rebuilt and deployed, and `surfaces` failed the same
stage the same way with it out of the tree. What is left to find is what the
failure actually needs — one campaign produces it, a freshly deployed DPU never
shows it, and every reduction of a campaign tried so far serves.

Evidence: the sampled run in
[`f-sample-20260822/`](f-sample-20260822/) with its balancer series, the traced
run in [`f-trace-20260822/`](f-trace-20260822/), the reductions in
[`reductions-output.txt`](f-spin-20260822/reductions-output.txt), and the
reverted-build run in [`f-revert-20260822/`](f-revert-20260822/).

### 1.3 The DPU exited twice, and the way it could

`dpumesh_dpu` was absent once during a campaign: no core file, no fault in the
log, the log ending on a routine statistics line, and the `screen` session it
runs under gone with it. It happened a second time while a deploy was restarting
the node agent — which revokes every registration the DPU holds — and the log
ended in the middle of that sequence, one routine `registration revoked` line
among sixty, half a minute before the next step found the process gone.

**The process has no way to end itself deliberately.** Nothing under `doca/` or
`src/` calls `exit()`, `_exit()` or `abort()`; no Rust in the adapter calls
`process::exit`. Every early return in `run_dpu_worker` logs an error first, and
the loop it ends in has no exit at all. So the process was ended from outside.

**And it was ignoring no signals:**

```text
SigIgn: 0000000000000000
SigCgt: 0000000100000000      one glibc-internal thread signal, nothing else
```

SIGPIPE's default action terminates the process **without a core file**, and
this kernel is configured to report no fatal signals
(`kernel/print-fatal-signals` and `debug/exception-trace` are both `0`), so
taking one leaves nothing at all: no core, no kernel line, and a log frozen
wherever it had reached. Sent to the running DPU, it reproduces the entry above
line for line:

```text
process present: 0
cores: 7 -> 7                       no new core
screen sessions: 481 -> 480         gone, not left as (Dead ???)
log bytes: 17898 -> 17898           last line a routine px_peer_stats_report
fault|abort|panic|signal in the whole log: 0
```

A Rust binary never has this problem: the runtime start-up its own `main` runs
installs `SIG_IGN` for SIGPIPE. The embedded proxy is a **static library linked
into a C `main`**, so that start-up never runs and the default stands — while
the proxy holds sockets to a control plane whose peers come and go, and a write
to one whose peer has just gone is exactly what raises it.

**Fixed** in `doca/dpu_main.c`: `signal(SIGPIPE, SIG_IGN)` before anything opens
a socket. The same signal now changes nothing:

```text
SigIgn: 0000000000001000            bit 12, signal 13
process present after SIGPIPE: 1, same pid
cores: 7 -> 7
```

What cannot be shown retroactively is that this is what ended those two
particular runs — neither left anything to test against, which is the whole
point of the mechanism. What can be shown is that the mechanism was present,
that it produces that exact signature on demand, and that it is gone. Evidence:
[`dpu-exit-sigpipe.txt`](f-spin-20260822/dpu-exit-sigpipe.txt), with the second
exit's own readings in
[`dpu-exit2-evidence.txt`](f-spin-20260822/dpu-exit2-evidence.txt).

The absence of a kernel message is worth carrying forward as a fact about this
DPU rather than as evidence: with `print-fatal-signals=0`, a fatal signal of any
kind leaves `dmesg` silent. What still rules out the signals that *do* dump —
SIGSEGV, SIGABRT, SIGBUS — is the missing core, with the limit unlimited, the
pattern a plain file and 15 GB free.

`stop_dpu` snapshots `screen -ls`, the kernel log, the core pattern and the log
tail into `$OUT` when it finds the process already absent; see
[3.9](#39-the-evidence-capture-stopped-the-deploy-it-was-added-to) for what that
addition cost before it worked.

## 2. The instrument

### 2.1 The gRPC client could stop answering after a run of failures

`bench_grpc` became unresponsive on its control port after a run in which every
request failed. The Pod stayed `Ready` with a restart count of zero, the native
client on the same node kept serving, and recovery was a rollout restart. The
control server accepts one connection at a time and runs the benchmark on the
accept loop's own thread, so a run that never ends is a client that answers
nothing for every stage after it.

**What could leave a run without an end.** A run's last act is to cancel every in-flight
call and shut each worker's completion queue down. The closed loop refills
itself from the completer thread, which decides to issue on
`now <= measure_end && !g_stop` and then issues *outside* the lock the sweep
holds. A refill that lands between the sweep and the shutdown is never
cancelled, and gRPC accepts it — `Shutdown` refuses new work only once the
queue has no outstanding event left, and during the drain it has. A call the
peer never answers then keeps `cq.Next()` from ever returning false, and the
join behind it never returns.

Both shapes seen in the campaign logs follow from that one call: a stage that
answered nothing while the next stage answered normally is that call completing
late, and a run of stages that all answered nothing is that call never
completing at all.

**The fix**, in `integrations/grpc/bench/bench_grpc.cc`:

- a call joins the worker's live set before it reaches gRPC, so a cancellation
  asked for in between is held on the context and applied when the call starts;
- `closing` ends issuance under the same lock the sweep takes, so no call
  outlives the sweep uncancelled;
- the sweep waits out the calls already admitted before shutting the queue down;
- a run is bounded by its own duration plus its channels' connect budget plus a
  margin, and a run that passes it reports the fault and exits rather than
  holding the control port — the Deployment then brings back a client that
  answers, which is what used to need a human.

**Not caught in the act.** Repeated runs each failing 120,000-140,000 requests
did not wedge a client built before the fix, so the above is a defect closed by
construction rather than a fault reproduced on demand. The campaign no longer
restarts the client between the mass-failure stages and the ones after them, so
the surfaces arm is now itself the test.

## 3. The harness

All ten are fixed. They are listed because each one put something false in the
record before it was found, or stopped the run that was making it: three
produced a wrong verdict that looked like a pass, two produced a failure that
read as a defect in the mesh, one wrote three rows whose columns did not line up
with the header above them, and two ended the run outright — one at the deploy
step it was written to inform, one on the first counter a freshly restarted DPU
had never incremented.

### 3.1 A missing reading was recorded as a refusal

`stage` parsed `rcnt=` and `fail=` out of the client's reply and defaulted both
to `0` when absent. A client that answered nothing therefore looked exactly like
a client whose requests were all refused, and every stage expecting a refusal
passed.

`bench/suite/policy_route.sh`, in `stage`: a reply with no `rcnt=` field is now
recorded as `nodata` and fails.

To see it work, hang the client as in 2.1 and run any scope: the stage reports
`the client did not answer — no reading` instead of a verdict.

### 3.2 A failed counter read became a count of zero

`ctl_event` ended in `sed 's/^$/0/'`, so an unreachable admin endpoint answered
`0`. The next delta then went negative — a process-global counter appearing to
run backwards, which cannot happen — and `max-admitted` gates compared against
garbage.

Seen as `admitted+=-1078` in a stage where the DPU had not restarted (same PID,
one start banner in the log).

`ctl_event` now answers `NA`, `ctl_delta` propagates it, and a gate that needs
the counter fails when it is unreadable. Both `policy_route.sh` and `inject.sh`
carried the same helper.

### 3.3 A campaign died on an empty metric grep

Under `set -o pipefail`, reading per-Pod request counts for a Service that had
served nothing yet failed the whole pipeline, and `set -e` ended the campaign
mid-stage. It first appeared as the cross-Service scope stopping after one
stage.

`grpc_service_requests`, `grpc_pod_requests` and the breaker's two readings now
tolerate an empty match.

### 3.4 A timeout was judged by the wrong latency

The `HTTPRoute` timeout stage asserted on what the client completed. The
client's latency includes a DMA round trip on both sides that a route timeout
does not cover, so a 1 ms timeout against a 1.26 ms client-observed p50 caught
single-digit requests and the stage's expectation was meaningless in both
directions.

The stage now reads the route's own
`outbound_http_route_request_statuses_total{error="REQUEST_TIMEOUT"}`.

### 3.5 A circuit breaker was measured against an outage

The arm took three shapes before it measured its subject. A breaker ejects an
endpoint so that traffic lands on the endpoint beside it:

- every endpoint failing leaves it nowhere to eject to;
- a failing backend a *route* chose by weight also leaves it nowhere — the
  weight already sent those requests there.

The failing endpoint has to be inside the balancer under test. It now joins the
Service under test through the Service selector
(`bench/k8s/policy/echo-grpc-broken.yaml`), and the stage declares the failures
the breaker must observe before it can act rather than requiring none.

### 3.6 A gRPC retry condition was written on a route that cannot carry one

`retry.linkerd.io/grpc: internal` was annotated on an `HTTPRoute`. A gRPC
failure is an HTTP 200 carrying `grpc-status`, and an `HTTPRoute`'s retry
conditions are HTTP status ranges — the policy controller reads that annotation
only where the route is gRPC-native. What did reach the proxy was the rest of
the annotations: a limit with no condition is still a retry policy, and the
proxy attaches it to every request the route matches. That is exactly what the
metrics said and why they said it — the four retry counters are created when a
request carries a retry policy, so they existed under the route's own labels,
and `retry_requests_total` stayed at `0` because no response could ever satisfy
an empty condition set.

The controller's own answer, with the old fixture applied:

```sh
linkerd diagnostics policy -n test-bench svc/echo-grpc-dpumesh 9092
#   retry:
#     conditions: {}          <- nothing survived the annotation
#     max_retries: 3
```

Both arms are now `GRPCRoute`s differing only in the annotations
(`bench/k8s/policy/grpcroute-retry.yaml`), where the same annotation arrives as
`conditions: {internal: true}`. `S3v` reads the route's own retry counter,
because an absorbed failure and a failure that never happened are the same
request to the client:

```text
S3a  fail=109  no retry policy
S3b  fail=0    retry_requests+=80  limit_exceeded=0  overflow=0
```

Every retry the DPU has ever emitted on this route has succeeded: 321 requests,
321 successes, nothing exceeded and nothing overflowed.

### 3.7 An inbound route was written in a kind its `Server` does not carry

The `AuthorizationPolicy` targeted a `policy.linkerd.io` `HTTPRoute` parented to
a `Server` whose `proxyProtocol` is gRPC. A gRPC `Server` carries gRPC routes:
that `HTTPRoute` is indexed under a protocol the `Server` does not speak, so
neither it nor the policy naming it appeared in the port's policy at all. The
port kept the deny-by-default a `Server` with no authorization has — which is
why the stage that should have admitted was indistinguishable from the negative
control that should not.

The inbound policy the destination Pod actually held:

```sh
linkerd diagnostics policy -n test-bench "po/$(kubectl get pod -n test-bench \
    -l app=echo-grpc-dpumesh -o jsonpath='{.items[0].metadata.name}')" 9092
#   Grpc: routes: [ { metadata: { Default: default }, rules: [...] } ]
#   — one default route, no authorizations anywhere
```

The fixture is now a Gateway-API `GRPCRoute` parented to the same `Server`, with
the `AuthorizationPolicy` targeting it; the route then carries the caller's
identity and the connection is admitted. The verdict that admits it is the
connection-level union [`design/DATA.md`](../../../design/DATA.md) describes —
refused exactly when no route would admit this caller, with which route a
request then matches not enforced — and the route kind is now published there as
the condition for reaching that evaluation at all.

```text
S10 refuses  fail=57    denied+=114
S11 serves   rcnt=5744  fail=0
S12 refuses  fail=21    denied+=42
```

### 3.8 A label containing a comma shifted a row's columns

Three fixture labels carry a comma, and the CSV is read column-wise, so those
three rows reported `rcnt` under `fail` and `fail` under `admitted` while every
row around them was aligned. The balancing rows carried the same hazard in their
`dist` field, which is a comma-separated list by construction.

Free text is now written with the separator replaced, in `stage`,
`counter_stage` and `lb_record`.

### 3.9 The evidence capture stopped the deploy it was added to

The snapshot [1.3](#13-the-dpu-exited-twice-and-the-way-it-could) asks for is taken
by `stop_dpu` when it finds the process already absent. `screen -ls` answers
non-zero when there is no session — which is the normal case for a process that
is already gone — and under `set -e` that ended the capture, the function, and
the deploy that called it, before it had even stopped the DPU. Two deploys died
on the line `=== Starting dpumesh_dpu ===` with a 60-byte snapshot beside them
holding one line: `No Sockets found`.

It was also asking the wrong user. The DPU's `screen` session belongs to root,
and the capture asked as the login user, whose socket directory is empty
whatever the process is doing — so `No Sockets found` is what it would have
answered with the session running.

Every command in the capture is guarded now and the function answers `0`
whatever happens, because it runs on the way to a redeploy and nothing it
collects is a reason to stop one. The reading that made 2.2's second occurrence
legible was taken by hand, from a DPU that had been down for twenty minutes,
because this is what the automatic one produced instead.

### 3.10 A counter with no sample became no answer at all

[3.2](#32-a-failed-counter-read-became-a-count-of-zero) gave `ctl_event` two
answers where it had one: `NA` for an endpoint it could not read, a count for
one it could. The count for a counter the DPU has never incremented was meant to
be `0`, produced by a `sed 's/^$/0/'` at the end of the pipeline — but a metric
name with no sample yields no line at all, and a substitution with no line to
act on writes nothing. The stage then evaluated `$(( - ))`.

It stayed hidden for as long as the DPU had been up long enough for every
counter in the family to exist. A freshly restarted DPU has none of them, and
the first stage to read one ended the campaign after the two that mattered had
already passed:

```text
F1 1 channel(s): backends=2 fail=0 take_errors+=0
F1 4 channel(s): backends=2 fail=0 take_errors+=0
policy_route.sh: line 112: -  : syntax error: operand expected
```

The default is applied to the value now rather than to a line that may not
exist — in `policy_route.sh` and in `inject.sh`, which carry the same helper —
and `ctl_delta` answers `NA` for anything that is not a count, because a stage
is better told its counter is unreadable than handed an arithmetic error.

## 4. Deployment

### 4.1 `kubectl wait` ran before the Pod object existed

`scale_up_with_wait` scaled a Deployment to one and immediately waited on a
label set that was still empty. `kubectl wait` fails at once on no matching
resources rather than waiting, so the deploy reported `failed to start` for a
Pod that started normally seconds later.

Latent until admission added a round trip to every Pod creation in the
namespace. Fixed by waiting for the object before waiting for its condition.

## 5. Documents

Each of these described a capability the code does not have. They are corrected;
they are listed because a reader would have believed them.

| Document | Claimed | Actual |
|---|---|---|
| `README.md` | "remote endpoints [are reached] by the RDMA peer channel" | the peer channel's transport is not yet bound, so a remote destination is refused |
| `README.md` | "Between nodes it is carried by the authenticated RDMA peer channel" | same, and it was a security claim |
| `README.md` | "There is no injection webhook, so a meshed Pod declares its own access" | one annotation and the webhook applies the access |
| `README.md` | "A backend is chosen per session… one [channel] does not [spread]" | the protocol-aware path chooses per request |
| `README.md` | an `HTTPRoute` "may not route [requests] into a different Service" | it may, and weighted `backendRefs` across Services work |
| `design/DATA.md` | "node-to-node confidentiality and mutual authentication are the RDMA peer channel" | a property the design assigns to a transport that is not yet bound |
| `design/DATA.md` | `TargetMismatch` refuses an endpoint in another Service | it guards only until an endpoint resolver is installed |
| `design/CONTROL.md` | the destination verdict "runs once per session" | once per destination a session reaches |
| `bench/report/data/node-density-sizing.md` | eight execution units, so the ring array binds at 32 | the device reports 32, so `MAX_PODS` binds and the ring array offers 128 |

The last one was mine, written earlier in this same work from
`DPA_THREADS_DEFAULT` — which is the fallback when the device query is
unavailable, not the count. The deploy log prints the real one:

```sh
grep 'dpa_threads=' /tmp/…/deploy.log      # dpa_threads='32'
```

`design/DATA.md` gained a statement rather than a correction: the route kind an
inbound authorization must be written in, which is 3.7.

## What is still true after all of it

On the build these fixes leave behind, run in one pass on a freshly deployed
DPU: `route` 5/5, `cross` 9/9, `fanout` **3/3**, `surfaces` 19/20.

`fanout` is the one that moved. Its four-channel stage returned no reading at
all while two workers were spinning; it now reports 40,581 and 40,760 across the
two backends with `fail=0`, and the eight admin endpoints answer where six did.
No worker has spun since.

The single failure is `S14`, which is [1.2](#12-the-protocol-aware-path-can-stop-accepting-connections)
and not a statement about failure accrual — `S13`, the stage that measures the
breaker, passes right before it. The four surfaces stages that used to fail are
3.6, 3.7 and the two readings 3.1 and 3.2 refuse to fake.

Numbers are in [`f-scope-20260822.md`](f-scope-20260822.md); the receipts are
[`f-spinfix-20260822/stages.csv`](f-spinfix-20260822/stages.csv), with the
pre-fix campaign kept beside them in
[`f-fix3-20260822-020539/`](f-fix3-20260822-020539/).

One column is still worth reading with care rather than fixing: `route_hits` can
go negative across a stage that tears a route down, because the proxy drops a
route's metric label set with the route. It gates nothing.
