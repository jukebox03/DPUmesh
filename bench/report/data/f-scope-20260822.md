# Function scope: what the campaigns decided

Five arms, one deployment, one build. Every stage is judged twice — by what the
client completed and by what the DPU's own counters say the enforcement point
decided — because traffic that stops without a matching verdict is not a policy
result, and traffic that flows without one is not a routing result.

Topology, placement and the 2.5 GHz clock are the frozen ones. Nothing here is
a capacity figure: these arms decide whether a feature works, and the request
counts are the volume a ten-second stage happened to carry.

## Per-request backend selection

`policy_route.sh fanout`, two backends of one Service, requests attributed by
the destination Pod the DPU's own `request_total` names.

| Client channels | Backend A | Backend B | `fail` | `take_errors` |
|---:|---:|---:|---:|---:|
| 1 | 8,329 | 8,326 | 0 | 0 |
| 4 | 48,467 | 47,355 | 0 | 0 |

One channel reaching both backends is the result. Spread now comes from the
route; it used to come from how many channels a client opened.

Re-run on the build that carries the fix for `findings-20260822.md` 1.1, both
stages repeat: 8,350 and 8,352 across the two backends on one channel, 40,581
and 40,760 on four, `fail=0` and `take_errors=0` throughout. The four-channel
stage is the one that returned no reading at all while two ARM workers were
spinning — which is what a worker that accepts nothing does to the sessions that
land on it, and not a statement about fan-out.

## Routing across Services

`policy_route.sh cross`, a route whose backend is a different Service.

| Stage | What it decided |
|---|---|
| X1 | 6,908 requests served by the other Service, `target_mismatches` flat |
| X2 | a `Server` on that Service refused all of them — 513 denials, nothing completed |
| X2b | withdrawing it restored service |
| X3 | weighted `backendRefs` split 18,386 / 18,587 across the two Services, `fail=0` |

X2 is the security half. The caller's own Service carries no policy at all, so
a stream refused there was graded by the Pod that receives the bytes rather than
by the Service the client addressed.

The stage cannot use an admitted-count gate: the caller still legitimately
reaches its own Service's backend, which no policy refuses, so what it asserts
is that the destination's denial counter moved. Every refusal the DPU logged
during the stage named the same destination Pod.

## Automatic injection

`inject.sh`, seven stages. The annotated Pod carries every piece of the patch —
control-plane label, `skip-inbound-ports`, device and library and attestation
mounts, PCI function, Service identity, preload shim, node affinity — and its
traffic takes a DPU inbound verdict. The same Deployment without the annotation
carries none of it and serves 393,425 requests over kernel TCP.

That second half is what makes the feature safe to turn on: an unpatched Pod is
a working Pod.

## Linkerd surfaces

`policy_route.sh surfaces`, twenty stages, nineteen decided. The twentieth,
`S14`, is `findings-20260822.md` 1.2: after an endpoint is withdrawn the
protocol-aware path stops accepting connections, and the stage that would have
read it gets `ERR connect failed on channel 0` instead of a reading. It is not a
statement about failure accrual — `S13`, the stage that measures the breaker,
passes right before it.

| Surface | Result |
|---|---|
| `HTTPRoute` request timeouts | enforced — the route's `REQUEST_TIMEOUT` counter moved |
| method matching | POST serves, GET matches nothing |
| header matching | `content-type: application/grpc` serves, `application/json` matches nothing |
| `GRPCRoute` | the called method serves, another method matches nothing |
| inbound `Server` | refuses by default, and refuses an unnamed identity |
| failure accrual | healthy endpoint 6,765, ejected endpoint 3 |
| HTTP/1.1 | 6,815 requests through the protocol-aware path, `fail=0` |
| retries | enforced — 136 failures reach the client without the policy, 0 with it, on 87 retries that all succeeded |
| route-level authorization | enforced — the route's caller served 6,470 requests, another identity refused with 272 denials |

Four of these needed the arm rebuilt before it measured its subject rather than
something beside it.

**A timeout is not measured by what the client completes.** The client's latency
includes a DMA round trip on both sides that the route timeout does not cover,
so a 1 ms timeout against a 1.26 ms client-observed p50 caught single-digit
requests. The route's own counter is the reading.

**A breaker is not measured against an outage.** It ejects an endpoint so that
traffic lands on the endpoint beside it. An all-failing backend leaves it
nowhere to eject to, and so does a failing backend a route chose by weight —
the weight already sent those requests there. The failing endpoint has to be
inside the balancer under test.

**A policy is not carried by every kind of route.** A gRPC failure is an HTTP
200 carrying `grpc-status`, so a gRPC retry condition lives only on a
`GRPCRoute`; annotated on an `HTTPRoute` it is dropped, and the limit beside it
still builds a retry policy with no condition, which the proxy attaches to every
request and which can never fire. The inbound half is the same shape: a `Server`
whose `proxyProtocol` is gRPC carries gRPC routes, so an authorization written
against a `policy.linkerd.io` `HTTPRoute` parented to it never appears in the
policy at all, and the port keeps its deny-by-default. Both arms read the
enforcement point's own counter now, because in both the client cannot tell an
enforced policy from a policy that was never built.

## What the campaign cost the instrument

The gRPC client could stop answering its control port after a run in which every
request failed, and three matching stages each fail ~15,000 requests in ten
seconds. The Pod stayed Ready with a restart count of zero. Every gRPC stage
that followed it in one chained run returned nothing and was recorded as a
refusal, which is a measurement error the harness now refuses to make: a stage
with no reply is `nodata` and fails.

A run's last act cancels every in-flight call and shuts its completion queue
down, and a closed-loop refill could be issued between the two — uncancelled,
and accepted, because a queue draining still takes work. A call the peer never
answers then holds the queue, the drain, and the accept loop behind it. The
client now admits a call to its live set before handing it to gRPC and closes
issuance under the lock the sweep takes, so no call outlives the sweep
uncancelled; and a run that outlives its own budget reports the fault and exits
instead of holding the port. The campaign no longer restarts the client between
the mass-failure stages and the ones after them.
